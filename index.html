01 Image provenance Solo project · 2026

ORIGIN: a dated, evidence-backed history of an image

Role Solo Code GitHub Evidence investigation page · demo film

Problem. An image reaches an analyst with a story attached. Reverse-image search lists pages, but not which copies are the same picture, when each one appeared, or where the story changes.

Approach. I built it alone. It takes one image and works in order: find copies through Google Lens, fetch and check each one, date it from evidence, group the copies by the story they tell, grade the sources, and cite everything. Every finding links to the stored source behind it (SHA-256 and fetch time), and the result exports as a JSON evidence pack or a PDF brief. Postgres constraints enforce the evidence rules: a claim needs a sighting, the audit log is append-only and API quota cannot be overspent.

Outcome. I built a matching evaluation: 18 sample photos, each edited 14 ways a repost is edited (crop, caption, watermark, recompression). Tuning the thresholds on it raised recall on edited copies from 75.4% to 93.7%, with 2 false positives in 306 unrelated pairs, both from one stereo pair of the same scene. The set is small and the thresholds were tuned on it, so the next step is a held-out test on real reposts (evals/report.md).

ORIGIN is not hosted. It runs locally with your own free-tier SerpApi and Gemini keys, and the repository README has the steps.

02 Data pipeline and analyst console Team coursework · 2026

School connectivity optimisation, Honduras

Role Data pipeline, analyst console and audit Solver Gurobi via Julia/JuMP Code GitHub Live analyst console

Problem. Honduras’s public school system is largely offline: of 15,492 public schools in the Giga dataset, 1,130 (7.3%) have a connection. Connecting a school needs a tower, then WISP equipment, then devices, in that order, on a fixed US$125M budget over five years.

Approach. The team formulated the plan as a multi-period mixed-integer linear programme in Julia/JuMP, solved with Gurobi, for two plans: one unrestricted, and one that must show annual progress. I built the data pipeline. I reverse-engineered the UNICEF–ITU Giga dataset to extract 15,000+ school records and merged cell-tower records into 7,297 sites. On my own I then rebuilt the results as a public analyst console where every figure cites its source. The build script asserts row counts and matching school IDs across both scenario files, so a data refresh cannot silently break the published figures.

Outcome. The unrestricted plan connects 12,409 of the 12,578 schools in scope (98.7%) by year 5. Requiring annual milestones brings that to 9,363 (74.4%), a loss of 3,046 schools, or 24.2 percentage points. I audited the model output against the team report and found 4 mismatches, which the repository records. One is duplicate site records in the milestone output, and another is a claim about unreached schools that the output files do not support.

03 Computer vision HackTheBurgh XIII · Best Use of Solana

PokerVis: a phone camera reads the cards on a real poker table

Role Card reading and backend, team of 3 Code GitHub Event HackTheBurgh XIII Evidence photograph below

Problem. A poker game played with real cards cannot settle its own bets. The table has to read the cards, and a wrong read must never move money.

Approach. A phone above a real poker table reads the cards, players bet from their phones, and each hand settles to their wallets in one Solana transaction. My part was the card-reading pipeline, built on YOLOv8, and the FastAPI backend and table state. A card only counts once it is read in 3 of the last 4 frames, so the ledger never acts on a misread. Ruairidh Colombini Allison and Jack Scott built the UI and the Solana mapping.

Outcome. The project won Best Use of Solana at HackTheBurgh XIII. It runs locally on Solana devnet with play money. It is not hosted.
